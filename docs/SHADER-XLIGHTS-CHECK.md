# Checking generated shaders in real xLights

**Why this document exists:** no automated session can run xLights. Everything the harness
proves - and it proves a lot - is proved by compiling against xLights' *contract*, transcribed
from its source (`smeighan/xLights`, `src-core/effects/ShaderEffect.cpp`, commit `858a5aea73f`).
The one thing only a human at a real xLights install can do is close the loop: load the files,
watch them render, and confirm the controls and colours behave. This is that checklist.

## What to test

The sample shaders live in `tools/shader-check/samples/` in this repo. They were generated by
the assistant with the current system prompt and pass the dual-dialect harness
(`node tools/shader-check/check.mjs tools/shader-check/samples/*.fs`).

## The steps

1. Copy the `.fs` files into your show directory's `Shaders/` folder (create it if it does not
   exist). xLights looks for shader files there by default.
2. In xLights, add a **Shader** effect to any model - a matrix shows the most, but try a
   1-pixel-high line model too, because that is the shape that breaks lazy shaders.
3. In the effect's settings panel, point the shader file picker at one of the copied `.fs`
   files.
4. Confirm, for **each** shader:
   - [ ] it loads with no error dialog and no complaint in the xLights log
   - [ ] it renders - moving colour, not a black rectangle and not a frozen frame
   - [ ] the controls declared in the header (speed and so on) appear in the effect panel, and
         dragging them visibly changes the effect
   - [ ] the **palette drives the colours**: change the effect's colour chips and the shader's
         colours follow, in the order the chips are set
   - [ ] it keeps moving smoothly for at least a minute (no build-up-and-stop, no visible loop
         seam)
5. Record pass/fail per shader, with xLights' exact error text for any failure.

## When something fails

File the failure with the shader text and xLights' error verbatim. Two places to look first:

- **Undeclared identifier** → the shader used something outside the portable subset and the
  harness should have caught it. That is a harness bug worth reporting on its own.
- **Renders black** → usually a uniform that never got a value. Check whether the input type
  is one xLights fills (float, bool, long, color, point2D) - and remember colour inputs come
  from the palette, not from their DEFAULT.

## What versions this was written against

The contract was read from `ShaderEffect.cpp` at commit `858a5aea73f` on 2026-08-21. If your
xLights is much newer and something disagrees, re-read the source before concluding the
shaders are wrong - the contract can move.
